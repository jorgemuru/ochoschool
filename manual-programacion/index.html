Propósito documental

Línea base final verificada: alta y modificación de eventos, filtros por rol, validaciones de usuarios, actualización de configuración Mobile, manejo consistente de fechas y control de cédula uruguaya.

Fundamentos

1. Alcance y arquitectura general

OchoSchool implementa una plataforma distribuida para la gestión de usuarios, eventos, convocatorias, asistencias, reclamos, justificaciones, constancias y reportes. La lógica central se concentra en una API REST desplegada sobre WildFly; el Website y la APP consumen esa API mediante JSON y reutilizan contratos DTO.

Navegador→Website JSF→API REST→JPA / Oracle
APP Android→Retrofit / JSON→API REST→JPA / Oracle

API REST

Expone recursos HTTP, aplica reglas de negocio, seguridad, transacciones y persistencia.

Website

Interfaz web administrativa y operativa basada en JSF, CDI y PrimeFaces.

APP Android

Cliente móvil orientado a estudiantes, tutores y analistas, construido con Kotlin y Retrofit.

Principios de diseño observados

  • Separación por capas y responsabilidades.
  • Contratos diferenciados de entrada y salida mediante DTO Request/Response.
  • Mapeo explícito entre entidades de persistencia y objetos de transferencia.
  • Autenticación basada en JWT y almacenamiento de contraseñas mediante BCrypt.
  • Reutilización de la API como punto único de acceso para Website y APP.
Módulo I

2. Módulo API REST

El módulo ochoschool.apirest es el núcleo transaccional. Está estructurado en controladores JAX-RS, EJB de negocio, DAO de persistencia, entidades JPA, DTO y mappers.

Controladores REST · rutas, verbos HTTP, códigos de respuesta
DTO + Mappers · contratos externos y transformación
EJB · reglas de negocio, validaciones y coordinación
DAO · consultas y operaciones de persistencia
Entidades JPA · modelo relacional Oracle

Responsabilidad de los controladores

Recibir JSON, validar el contexto de la solicitud, invocar el servicio adecuado y construir respuestas HTTP coherentes. Los controladores cubren usuarios por subtipo, eventos, convocados, reclamos, justificaciones, constancias, mantenimientos y reportes.

Responsabilidad de los EJB

Aplicar reglas de negocio, coordinar operaciones entre entidades, controlar duplicados, generar nombres de usuario, gestionar estados y encapsular la interacción con los DAO.

DTO Request/Response

Los RequestDTO limitan los campos aceptados por una operación; los ResponseDTO presentan información preparada para cada cliente sin exponer directamente el modelo persistente.

Mappers

Centralizan la conversión entre entidad y DTO, evitando conversiones dispersas dentro de controladores o clientes.

Flujo de una operación

HTTP Request→Controlador→EJB→DAO→Oracle→ResponseDTO
Convención recomendada: mantener los códigos 200/201 para éxito, 400 para solicitud inválida, 401 para falta de autenticación, 403 para falta de autorización, 404 para recurso inexistente, 409 para conflictos de unicidad y 500 para fallos no controlados.
Módulo II

3. Módulo Website

El Website combina páginas XHTML, componentes PrimeFaces, beans CDI y clientes HTTP. Su función es presentar operaciones de gestión y convertir acciones de interfaz en invocaciones a la API REST.

XHTML / PrimeFaces→Bean CDI→ApiClientAux / servicios→API REST

Presentación

Las páginas se organizan en layout, cabecera, pie, navegación y pantallas funcionales. Los formularios utilizan mensajes JSF, diálogos, tablas y filtros.

Beans

Conservan el estado de pantalla, realizan validaciones previas, preparan DTO, invocan servicios y traducen resultados o errores a mensajes para el usuario.

Integración HTTP

Las clases cliente serializan solicitudes, aplican el JWT cuando corresponde, interpretan códigos HTTP y deserializan ResponseDTO.

Seguridad web

Los filtros y utilidades de sesión restringen páginas, administran el token y agregan encabezados de seguridad a la respuesta.

Patrón de interacción recomendado

Vista XHTML → método del Bean → RequestDTO → cliente HTTP
→ endpoint REST → ResponseDTO → actualización del Bean → mensaje/navegación

Los errores funcionales deben mantenerse separados de los errores de conectividad. Por ejemplo, un HTTP 409 debe convertirse en una excepción de API con código y mensaje, no en una IOException.

Módulo III

4. Módulo APP Android

La aplicación móvil utiliza Kotlin, AndroidX, View Binding, Fragments, RecyclerView y Retrofit. La URL base se incorpora mediante BuildConfig.API_BASE_URL, permitiendo diferenciar ambientes sin modificar el código fuente.

UI

MainActivity, HomeActivity y Fragments especializados organizan navegación y casos de uso.

Servicios

RetrofitProvider, ApiServicios y UsuarioServicio concentran la comunicación remota.

Datos

DTO y modelos Kotlin reflejan los contratos JSON; adaptadores personalizados resuelven fechas, Base64 y arreglos binarios.

Dependencias principales verificadas

AndroidX Core/AppCompatMaterial ComponentsConstraintLayoutRetrofit 2.9.0Gson converter 2.9.0OkHttp logging 4.12.0RecyclerViewDataStore PreferencesGoogle MapsView Binding

Flujo móvil

Fragment→Retrofit→API→DTO→Adapter / RecyclerView
Configuración: en emulador o dispositivo físico la dirección localhost referencia al propio dispositivo. Debe configurarse una URL accesible desde la red del equipo o el alias del emulador que corresponda.
Arquitectura transversal

5. Integración entre módulos

Formato de intercambio

Los clientes envían y reciben JSON. Los nombres y tipos definidos en los DTO deben mantenerse coordinados entre API, Website y APP.

Autenticación

Luego del inicio de sesión, el token JWT se conserva en el cliente y se envía en el encabezado de autorización para recursos protegidos.

Archivos adjuntos

Las justificaciones y otros adjuntos binarios se transportan mediante representaciones Base64 o arreglos JSON según el contrato, por lo que existen serializadores y deserializadores específicos.

Fechas

La compatibilidad entre Java, JSON y Kotlin requiere una convención estable para timestamps y fechas legibles, evitando interpretaciones distintas entre clientes.

Contrato compartido

{
  "documento": 12345678,
  "primer_nombre": "Nombre",
  "primer_apellido": "Apellido",
  "tipo_usuario": "ESTUDIANTE"
}

Los ejemplos de configuración deben usar nombres de host, usuarios y secretos de referencia. Los valores operativos se mantienen fuera del contenido público del manual.

Protección y acceso

7. Seguridad

Contraseñas

Las contraseñas se procesan con BCrypt. La comparación se realiza contra el hash persistido y nunca debe registrarse la contraseña en texto plano.

JWT

El token representa la sesión autenticada y debe validar firma, expiración e identidad. Los clientes lo envían únicamente a través de canales seguros.

LDAP

El módulo incluye integración LDAP para autenticación institucional. Las rutas, credenciales de servicio y parámetros se externalizan.

Headers y filtros

El Website incorpora filtros de autenticación y encabezados para reducir exposición a contenido embebido, MIME sniffing y otros vectores comunes.

Reglas operativas

  • No incluir secretos, tokens, contraseñas ni cadenas de conexión dentro del repositorio público.
  • Usar HTTPS en ambientes accesibles desde redes no confiables.
  • Invalidar la sesión del cliente al expirar o rechazarse el JWT.
  • Aplicar autorización por rol en la API, no solamente ocultar controles en la interfaz.
  • Registrar eventos de seguridad sin incluir datos confidenciales.
Entornos

8. Configuración

API REST

apirest.properties, persistence.xml y configuración de WildFly definen base de datos, JWT, LDAP y recursos.

Website

app.properties y utilidades de configuración determinan URL de API y parámetros del cliente.

Android

API_BASE_URL se resuelve desde propiedades de Gradle o local.properties y se compila en BuildConfig.

Ejemplo de variables

API_BASE_URL=https://api.ejemplo.edu/ochoschool/api/
DB_DATASOURCE=java:/jdbc/OchoSchoolDS
LDAP_URL=ldap://directorio.institucional:389
JWT_SECRET=${JWT_SECRET}
Los archivos de configuración operativa deben mantenerse separados por ambiente: desarrollo, prueba y producción.
Operación

9. Compilación y despliegue

API REST y Website

  1. Importar cada proyecto como Dynamic Web Project en Eclipse compatible con Java 17.
  2. Verificar facetas, runtime de WildFly y librerías del proyecto.
  3. Ejecutar Project → Clean y confirmar que se generen las clases.
  4. Exportar cada módulo como archivo WAR.
  5. Desplegar primero la API y luego el Website.
  6. Validar datasource, configuración LDAP, rutas de archivos temporales y permisos del servicio.

APP Android

  1. Abrir el proyecto en Android Studio y sincronizar Gradle.
  2. Definir API_BASE_URL para el ambiente.
  3. Compilar con SDK 34; mínimo SDK 24 y objetivo SDK 33 según el proyecto final.
  4. Generar APK de depuración o paquete firmado para distribución.
  5. Validar conectividad desde el dispositivo y permisos requeridos.

Orden de verificación

Oracle→WildFly / datasource→API→Website→APP
Evolución

10. Guía de mantenimiento

Agregar una nueva entidad funcional

  1. Crear o ajustar la entidad JPA y sus relaciones.
  2. Crear DAO con operaciones necesarias.
  3. Crear EJB para reglas de negocio.
  4. Definir RequestDTO y ResponseDTO.
  5. Crear Mapper bidireccional cuando corresponda.
  6. Exponer endpoints en un controlador REST.
  7. Agregar métodos de cliente y DTO equivalentes en Website.
  8. Crear bean y pantalla XHTML.
  9. Agregar modelos, DTO, servicio Retrofit y Fragment en Android.
  10. Probar códigos HTTP, validaciones, autorización y concurrencia.

Checklist de cambio transversal

Contrato

Nombre de campos, nulabilidad, formato de fecha y representación de entidades relacionadas.

Persistencia

Restricciones, claves foráneas, transacciones y rollback.

Clientes

Deserialización, mensajes de error, estados de carga y actualización de listas.

Seguridad

Rol autorizado, token requerido y exposición mínima de datos.

11. Troubleshooting

HTTP 409 mostrado como conexión

Revisar que el cliente lance una excepción funcional de API y no envuelva toda respuesta no exitosa en IOException.

ORA-00001

Validar duplicados antes de persistir y conservar la restricción en base de datos. Capturar la carrera de concurrencia y devolver 409.

HTTP 401 / token

Comprobar encabezado Bearer, expiración, firma, ruta protegida y limpieza de sesión en el cliente.

ClassNotFound en WildFly

Limpiar proyecto, comprobar build/classes, facetas, librerías y contenido real del WAR.

Upload / NoSuchFileException

Revisar límites de tamaño, directorio temporal de Undertow, permisos y persistencia inmediata del contenido.

Gson: BEGIN_ARRAY vs STRING

Alinear el contrato del archivo adjunto e instalar el adaptador correcto para Base64 o arreglo JSON.

DateTimeParseException

Confirmar si la API devuelve epoch, fecha ISO o formato local y centralizar la conversión.

Android no conecta

Evitar localhost en dispositivo físico; comprobar IP, puerto, firewall, HTTP cleartext y ruta base.

JSF bean nulo

Verificar alcance, nombre CDI, inyección y consistencia entre @Named y referencias EL.

Campo clave vacío al modificar

No sobrescribir el hash cuando la contraseña no cambia; separar operación de actualización de credenciales.

Calendario sin edición de hora

En PrimeFaces 8, usar p:calendar con showTime="true" y timeInput="true" para campos que requieren hora y minutos.

FaceletException por declaración XML

Las composiciones Facelets deben comenzar directamente con <ui:composition> o mantener una única declaración XML en la primera posición absoluta.

lateinit no inicializado en Android

Usar propiedades anulables para selecciones asíncronas, asignar el valor inicial al cargar cada spinner y validar antes de construir el DTO.

Activity creada sin usuario

No acceder al singleton de sesión durante la construcción de la Activity. Obtener el usuario dentro de onCreate() mediante una consulta segura.

Estado final

12. Cierre funcional y correcciones finales

La línea base documentada incorpora los ajustes de cierre aplicados sobre los tres módulos. Estas correcciones forman parte del comportamiento actual del sistema y deben conservarse en futuras evoluciones.

Eventos Website

Los formularios de alta y modificación utilizan selección visual de fecha y hora. Se valida que la fecha de finalización no sea anterior a la fecha de inicio y se procesan correctamente los campos requeridos antes del PUT.

Modalidades activas

La carga de modalidades del formulario considera únicamente registros con estado activo. Los combos de filtro mantienen su finalidad independiente sobre los eventos visibles.

Visibilidad del Tutor

El conjunto base de eventos se reconstruye según el usuario autenticado. Aplicar o reiniciar filtros no permite que un Tutor recupere eventos ajenos.

Filtros robustos

Los filtros de Eventos y Justificaciones conservan los parámetros existentes, admiten valores nulos de forma segura y restablecen la lista respetando permisos y contexto.

Configuración Mobile

Los datos modificados actualizan el usuario en memoria, los spinners se inicializan sin propiedades lateinit pendientes y la navegación vuelve al fragmento de inicio sin crear una nueva Activity.

Fechas Mobile

La fecha de nacimiento admite formato ISO local yyyy-MM-dd y variantes con zona horaria. La pantalla utiliza un formato coherente para mostrar, validar y enviar el dato.

Validaciones Mobile

Nombre, apellido, teléfono y contraseña aplican reglas de longitud y caracteres. Los campos relacionados con ITR, género, departamento, localidad, área y rol se validan antes de construir el request.

Cédula uruguaya

El alta y la modificación administrativa validan longitud, contenido numérico y dígito verificador. La pantalla de datos propios conserva la cédula original cuando el usuario actualiza su perfil.

Flujo estabilizado de modificación de usuario Mobile

ConfigFragment→Validaciones→DTO Request→Retrofit PUT→UsuarioServicio→HomeFragment
Baseline de cierre: ochoschool.apirest(13), ochoschool.website(15) y pft2025app(13). La documentación debe actualizarse nuevamente si cualquiera de estos módulos cambia.

15. Glosario

DAO

Objeto de acceso a datos que encapsula consultas y persistencia.

DTO

Objeto de transferencia que define el contrato entre capas o sistemas.

EJB

Componente empresarial usado para lógica de negocio y transacciones.

JAX-RS

Especificación Java para construir servicios REST.

JPA

Especificación de persistencia y mapeo objeto-relacional.

JWT

Token firmado usado para representar autenticación y claims.

CDI

Modelo de inyección de dependencias y administración de beans.

JSF / PrimeFaces

Framework de componentes web del lado servidor y biblioteca visual asociada.

Retrofit

Cliente HTTP declarativo utilizado por la APP Android.

Mapper

Componente que transforma entidades en DTO y viceversa.
